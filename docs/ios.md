# iOS client

The iOS client is a container app plus a custom keyboard extension under `ios/`. It shares `VoiceDraftCore` with the Mac app and keeps the same rules: users bring their own provider keys, calls go straight from the device to the configured provider, nothing is proxied, and the only server the app talks to is a VoiceDraft sync server chosen by the user. This page owns the iOS boundaries; [architecture.md](architecture.md) owns everything shared with the Mac app.

## Scope

| Included in the first cut | Deliberately excluded |
| --- | --- |
| In-app dictation with Polish, Translate and Ask using the shared adapters and prompts | Edit mode (no selection access from a keyboard) |
| Sync download/upload with the existing envelope and `/v1/sync` protocol | Per-app writing styles and screen context (the extension cannot identify its host app) |
| Vocabulary, styles and provider profiles from `SharedSettings` | Agent context discovery (`AgentContextScanner` reads Codex/Claude folders that do not exist on iOS) |
| Local history, plain JSON like the Mac, never synced | Self-updating (the App Store updates the app) |
| Keyboard extension, voice only: hold to talk through the container app, insert last result, and four basic keys (globe, space, delete, return). Typing is left to other keyboards | Hosted-sync purchase and any in-app purchase (follows later, in the container app only) |
| Choosing the active speech and writing profiles and entering their API keys | Creating or editing model profiles on the phone (they arrive through sync or the built-in defaults) |

## Process model

Apple keyboard extensions have no microphone access, even with Full Access. Recording therefore happens only in the container app. Three flows exist:

1. **In-app dictation.** Hold the record button, release, the app runs the shared speech and writing pipeline, shows the result, copies it on request, appends it to local history and writes it to the app group as the latest result.
2. **Insert from the keyboard.** The keyboard reads the latest result from the app group and inserts it through `textDocumentProxy`. This needs Full Access because the app group container is gated by it.
3. **Record from the keyboard.**
   - *App on standby* (`app-status.json` eligible **and a fresh app check answered**): hold to talk. The keyboard posts `take.start` and `take.stop` Darwin notifications; the app records in the background, runs the pipeline, writes the result to the app group and posts `result.updated`; the keyboard inserts it.
   - *App not on standby*: the talk button reads "Tap to dictate (opens VoiceDraft)". A tap writes `pending-take.json` (`{ id, startedAt, source: "keyboard" }`) to the app group and opens `voicedraft://record?take=<id>&source=keyboard` through `ContainingAppOpener`, which tries three strategies in order and stops at the first success: (1) `NSExtensionContext.open`; (2) walk the responder chain from the input view controller to the `UIApplication` instance inside the extension process, matched by class (`UIWindowScene` also answers `openURL:options:completionHandler:` on iOS 17+ but raises inside an extension, which crashed the keyboard on 2026-10-22), and call that public method with empty options, or `openURL:` when only that answers; (3) `UIApplication` looked up with `NSClassFromString`, `sharedApplication` read through key-value coding and checked to be a `UIApplication`, and the same call. Each strategy is retried once with the scheme spelled `VoiceDraft://` only after the lower-case form returned false. On iOS 27.0.1 `NSExtensionContext.open` returned false for this keyboard, which is why strategies 2 and 3 exist. The calls go through selectors because `UIApplication.shared` and `open(_:options:completionHandler:)` are unavailable to extensions at compile time. On success the status line shows "Opened VoiceDraft (method N)" briefly; when every strategy fails the marker is deleted and the line lists each result, for example "Open failed: ext=false/false · chain=none · app=false". Every try is appended to `open-attempts.json` in the app group (strategy, URL form, result, timestamp; last 20), and Settings > About shows the latest one. The app handles the link in `onOpenURL` (cold launch included) without confirmation: it starts a keyboard take with that id (the microphone permission prompt comes from the audio start), starts or extends standby, and shows a full-screen recording view with elapsed time, level, Finish, Cancel and the hint that the user can go back and finish from the keyboard. The development build attempts automatic return for a fresh matching keyboard hand-off (see below); the system back affordance remains the fallback; the recording view says so. The reappearing keyboard reads the marker: while no `SharedResult` with that id exists it shows "VoiceDraft is recording…" and a Finish button that posts `take.stop`, but only when `app-status.json` shows the app working on that take: `state` is `recording` or `processing`, `updatedAt` is at most 2 minutes old (the app rewrites the status every 30 s while a take records), and `takeID` is absent or equals the marker id. Otherwise, on appearance or on Finish, the keyboard deletes the marker, shows the normal talk button and the notice "The last take did not start", and never waits in processing for a result that cannot arrive. When the result with that id arrives (notification or the 0.5 s poll) the keyboard inserts it and deletes the marker. A marker older than 10 minutes is deleted. Processing after Finish waits at most 30 s for a take recorded in the app (60 s for a standby take), and the app holds a background task during processing so it is not suspended once the microphone closes.

A standby lease survives force-quit, so `app-status.json` alone never authorizes background recording. On each eligible tap the keyboard enters a blue Connecting state, writes a fresh UUID challenge to `app-check-request.json`, and posts `app-check.requested`. The running app answers in `app-check-reply.json` with that UUID and its current readiness/busy state, then posts `app-check.replied`. Only a matching live ready reply permits `take.start`; no reply within 500 ms or an unavailable reply takes the same tap through the normal containing-app launch. The check itself never opens the microphone. Old replies are ignored, leaving the keyboard cancels a pending check, and a short tap released while checking still locks the eventual recording; releasing a long hold before a start cancels it. App-opening state is retained before the open callback, so switching away cannot strand a take or restart timers off screen.

While recording or processing, the visible keyboard checks the app again at most every two seconds, and checks immediately after Finish. A matching completed result wins over an absent/idle reply. Otherwise a missing reply exits the waiting state, clears this keyboard's pending marker and makes the next tap open the app; a best-effort stop prevents a temporarily unresponsive recording process from continuing capture after recovery. The existing 30/60-second processing limits remain provider-progress bounds, not dead-process detection. Challenge files contain only IDs, timestamps and state, with no audio or text.

Takes are capped at 10 minutes like the Mac; Core's chunking handles provider limits. A take that fails (no speech, missing key, provider error) writes an empty latest result and still posts the result notification, so the keyboard stops waiting and inserts nothing. Keyboard takes carry no application name, and history labels them "Keyboard".

### Standby and microphone readiness

`IOSPictureInPictureKeepAlive` uses a video-call Picture in Picture controller. It creates its source view in the key window and starts **while both the application and the source scene are foreground-active**. Starting explicitly from `willResignActive` was reproduced on the iPhone (iOS 27.0.1) as `AVKitErrorDomain(-1001)`: the content source's scene was no longer foreground-active. The controller observes `isPictureInPicturePossible`, bounds unavailable preparation and background transition to five seconds (a prepared controller may wait in the foreground), and reports real readiness from `pictureInPictureControllerDidStartPictureInPicture`. Creating the controller alone never advertises background availability to the keyboard. Closing PiP ends standby; a take already running remains finishable, including its background processing interval.

The plain UIKit microphone/status content renders correctly on this device. The earlier suspicion that an `AVSampleBufferDisplayLayer` was required for this failure was not borne out: changing the startup timing enabled PiP with the existing content. Typeless documents PiP, but does not disclose all its current internal implementation; AgenBoard's sample-buffer renderer is a reference, not a proven prerequisite for VoiceDraft.

The microphone and PiP share `IOSAudioSessionController`: `.playAndRecord`, `.measurement`, `[.allowBluetooth, .mixWithOthers, .defaultToSpeaker]`. The session stays active through standby; no microphone engine remains between takes. Stopping a take closes the input **before recognition starts**. Manual standby briefly establishes real microphone input in the foreground, discards that audio, then closes it again. A keyboard-opened take establishes input through its normal recording path. This preparation matters: a cold background-only `engine.start()` was observed to succeed with zero PCM, while foreground preparation followed by two background takes produced data in both. `IOSAudioCapture.start()` waits for the first converted PCM buffer (three-second timeout per attempt), so successful engine construction alone is not recording readiness. If HFP negotiates a new input format before readiness, capture rebuilds the engine after 300 ms, at most twice, keeping the session active. Once ready, configuration changes still end the take. Stop/cancellation invalidates the startup generation; session interruption/reset observers remain installed between engines. Automatic return waits for real audio readiness as well.

Device tests verified that foreground preparation enabled later background takes and that the microphone indicator turned off between takes.

The earlier silent-output engine was removed. Its category-switch experiments failed with `!int`, and fresh background microphone startup under a silent output failed with `what`; those results do not establish that PiP cannot work. The optional **Keep microphone open during standby** fallback remains available but holds the indicator on. Standby defaults to 15 minutes (Off, 5, 15, 30); a keyboard take starts or extends the deadline, while the periodic status refresh only renews the lease within that deadline. The session deactivates when neither standby nor a take needs it. Bluetooth HFP routing and background eligibility after calls/route changes still need broader device coverage.

### Development-build hidden standby

Debug now starts PiP with a `300 × 0.1 pt` preferred content size, transparent clipped content, and controls style `2`. The private `setControlsStyle:` call is confined to `#if DEBUG` and validates the Objective-C method signature before calling it. On the tested iPhone 17 / iOS 27.0.1 the system rounds the actual content and PiP window to `380 × 0 pt`; it remains active and is not suspended. This does not enter the system's edge-stashed state, so there is no edge arrow and no manual drag is needed. One second after `didStart`, a visible or missing window fails standby explicitly instead of silently accepting a visible fallback. The existing Home control and fixed deadline stop hidden standby.

The mechanism was researched in [Yoroin's GlobalRefresh-PiP](https://github.com/Yoroin/GlobalRefresh-PiP/tree/1b62341c1d62308962fb3656192d6783631aa00c), based on [CaiWanFeng/PiP](https://github.com/CaiWanFeng/PiP), and independently implemented here without third-party code, dependencies, global method hooks, or refresh-rate machinery. [Typeless's published PiP instructions](https://www.typeless.com/help/release-notes/ios/picture-in-picture) describe manually dragging to the edge; they do not document this fully hidden implementation.

Debug device tests verified background audio capture after standby with the PiP window hidden. Coverage was limited to the tested OS and audio routes.

### Development-build automatic return

The user authorized undocumented-system-behavior experiments in development builds. `VDHostNavigation` is inert in Release. In Debug, the keyboard enables `_UIKeyboardArbiterClient` early and reconnects it when the keyboard appears. At the microphone tap it accepts `sourceBundleIdentifier` only when the arbiter's process ID matches the keyboard controller's host process ID. It stores no host cache: the optional bundle identifier belongs only to that `PendingTake`.

The containing app accepts return metadata only from a matching keyboard marker at most 15 seconds old, never from arbitrary URL parameters. It waits for microphone input and standby preparation, cancels the return when the take is cancelled, and makes one attempt while foreground-active. It tries `LSApplicationWorkspace.openApplicationWithBundleID:` for a validated host, with the system navigation back action as a fallback. Missing runtime support leaves the existing manual-return UI available. `suspend` is not used. These are compatibility experiments, not supported Apple APIs or a release/App Store approval claim.

Debug diagnostics are bounded to the last 200 metadata events in `app-diagnostics.json` / `keyboard-diagnostics.json` in the App Group. They contain lifecycle steps, take IDs, host bundle IDs, error domains/codes, and PCM counts in the probe; never audio samples, recognized text or credentials. The explicit `--standby-device-probe` launch mode uses temporary/in-memory app state. `--probe-prime-microphone --probe-return-settings --probe-visual` exercises local capture and return to Settings; `--probe-model-return` exercises the actual model with temporary HTTP-only configuration and always cancels before recognition. Hidden PiP is the Debug default; `--probe-visible-pip` enables the visible comparison only in probe mode. `--probe-long-standby` waits 90 seconds before the first background capture. `--probe-built-in-microphone` prefers the built-in input during initial preparation, but iOS may subsequently choose Bluetooth HFP; it is not a fixed-route guarantee.

## Trust boundaries

| Location | Holds | Never holds |
| --- | --- | --- |
| App group container `group.com.voicedraft` | Latest result (id, text, mode, timestamp), app status (state, lease expiry, update time, id of the take in progress, last standby error text), transient recording meter (take id, latest measured amplitude, subsecond PCM timestamp), latest app-check challenge/reply (request id, request time, ready/busy/unavailable state, active take id), keyboard presence marker (timestamp, full-access flag, version), pending keyboard take marker (take id, start time, source, optional validated host bundle identifier), the keyboard's last 20 tries to open the app (strategy, URL form, result, timestamp), the UI language preference | API keys, sync token, passphrase, history, audio |
| Container app Keychain | API keys, sync token, sync passphrase | — |
| Container app documents (file protection complete) | Settings JSON (including vocabulary, like the Mac), history JSON capped at 500 entries, a local JSONL usage log | Retained audio (not implemented on iOS) |
| Keyboard extension | Nothing persistent of its own | Any network code. The extension does not link the provider clients and makes no requests |

Recording feedback uses `recording-meter.json`, separate from the app-status lease. During keyboard takes the app publishes the latest PCM RMS amplitude at most 10 times per second, timestamped when PCM actually arrived. The keyboard polls only while its recording UI is visible and Full Access is enabled. It rejects samples from another pending take, samples older than the current take, future timestamps and samples older than 400 ms. Missing/stale input clears the waveform; stop, cancellation and failure remove the meter file. The view draws one continuous white curve with tapered ends, with its whole envelope driven by the current amplitude and 100 ms transitions between updates. The curve shape is a volume visualization, not a PCM trace: phase advances only on nonzero meter updates, silence contracts to a flat line, and missing input resets immediately. Reduce Motion uses a fixed curve shape and immediate level changes. No PCM, audio history, credentials or network calls are added to the extension.

The keyboard requires Full Access only for the app group. Because the extension contains no networking and is open source, the Full Access warning can be answered with a verifiable statement rather than a promise.

Keyboard setup. The app opens Settings > VoiceDraft through the public `UIApplication.openSettingsURLString` and shows three steps: tap Keyboards, turn on VoiceDraft, turn on Allow Full Access. The VoiceDraft switch on that page adds the keyboard, so the guide tells the user not to go through General > Keyboard > Add New Keyboard. No private `App-prefs:` URL is used. The app learns that the keyboard is enabled only from `keyboard-presence.json`, which the keyboard writes to the app group whenever it appears with Full Access. It never inspects `UITextInputMode`. The marker can go stale: it stays after the keyboard is removed or Full Access is revoked, because the extension can no longer reach the container then, so the app shows its timestamp.

The sync server sees exactly what it sees from the Mac: one ciphertext envelope, its size, revision numbers and access timing. History and audio never leave the device.

Pairing. The app registers the `voicedraft` URL scheme (`CFBundleURLTypes`, role Editor) and handles `voicedraft://sync?...` links from `onOpenURL`, including cold launches, and from **Paste pairing link** on the Sync screen. That button reads the clipboard only when tapped, so iOS shows no paste prompt when the screen opens. Core's `SyncPairingLink` validates the link (format in [architecture.md](architecture.md#encrypted-sync-protocol-v1)). A valid link only waits in memory until the user confirms "Connect to <host> and download the server copy?". Connect then runs the same configure path as manual entry (Keychain token and passphrase, server URL, revision reset for a new server identity) and an explicit download, and reports the revision and profile count or the error. The link itself is never stored. Scanning the Mac's QR code with the Camera app opens the same link.

## Audio path

The Mac feeds `PCM16Audio` from an `AVCaptureAudioDataOutput` sample buffer. iOS uses an `AVAudioEngine` input tap, converts to 16 kHz mono PCM16 with `AVAudioConverter`, and feeds the same `LiveAudioFeed` for WebSocket adapters or buffers a WAV for HTTP adapters. The audio session uses the shared `.playAndRecord` configuration described above and stays active through standby even while the microphone engine is stopped.

## Settings and localization

`SharedSettings` is reused unchanged; `applicationStyles` and `screenContextExcludedApps` are ignored on iOS. Device-local options live in an iOS `DeviceSettings` variant. `VoiceDraftCore` resources load through `Bundle.module`; the language preference lives in the app-group `UserDefaults` suite so the app and the keyboard agree.

## Experiment: direct keyboard recording

Status: falsified on iOS 27.0.1 (2026-10-23). Hypothesis: since iOS 26.4, a custom keyboard with Full Access can record audio itself once its containing app holds the microphone permission, which would remove the app switch for dictation. The evidence came from other people's reports: Typeless, 微信输入法 and 豆包 reportedly stopped switching to their apps for voice input around March 2026, shortly after iOS 26.4. A Debug-only "Test keyboard recording" button in the keyboard (`MicrophoneProbe`) ran `setCategory(.record, .measurement, [.allowBluetooth])`, `setActive(true)` and a 1 s `AVAudioEngine` input tap that only counted buffers and the peak level. Result on the device, two runs with identical outcomes: permission "granted", inherited from the container app, with no prompt shown; `setCategory(.record)` and `setActive(true)` succeeded; the input format read 48000 Hz 1 ch; `engine.start` failed with OSStatus 2003329396 'what' (`kAudioHardwareUnspecifiedError`); 0 buffers arrived. Conclusion: the keyboard extension process gets no microphone IO, even with Full Access and the permission granted. This result supports using a resident container app here; it does not establish the internal implementation of Typeless or 微信输入法. The probe code (the keyboard button, `MicrophoneProbe`, `KeyboardProbe`, `probe-results.json`, the Settings > About line and the keyboard's `NSMicrophoneUsageDescription`) was removed after this result; it lives in the pre-squash history kept on the local branch `keyboard-experiments` for a future re-test on a later iOS version.

## App Store constraints that shape the design

- The keyboard offers a next-keyboard button and its basic keys without Full Access; voice features stay visible but disabled and explain in one line why Full Access is needed instead of failing silently.
- The extension contains no marketing and no purchases. It opens only its own containing app, only when the user taps the talk button and the app is not on standby. It first uses the public `NSExtensionContext.open`, which iOS 27.0.1 refused for this keyboard. It then reaches the extension process's `UIApplication` through the responder chain (or by class name) and calls its public `openURL:options:completionHandler:` / `openURL:` methods. This is the approach the keyboard ecosystem uses, for example the open-source KeyboardKit library, and the app owner approved it for this app. Apple regards it as an implementation detail that may change; Apple DTS on the developer forums (thread 826851): "There's no such thing as a 'private API'. … Everything else is an implementation detail." DTS also confirmed there is no public API for the return trip to the host app. No `App-prefs:` URL is used. The development-build return experiment can reopen the current keyboard host; the extension itself opens only VoiceDraft. Guideline 4.4.1 says keyboards must not launch other apps besides Settings. Opening only the containing app for user-initiated dictation is the pattern shipped by Wispr Flow, Typeless and 微信输入法, and Apple documents no supported API for it (developer forums threads 843118 and 826851, FB22247647). Whether any strategy succeeds on a given iOS version is not guaranteed, so the keyboard shows each result and records it in `open-attempts.json`. If review objects or iOS closes the path, the fallback remains standby-only mode: remove `ContainingAppOpener` and keep "Start standby now" plus Darwin notifications.
- Apple DTS confirmed there is no supported public automatic-return API. Debug now experiments with validated host identity and a system navigation fallback as described above; Release retains manual return. The earlier `suspend` trial went to the Home Screen and remains removed.
- Guideline 2.5.4 restricts background audio to its intended purpose. Standby keeps the app resident between keyboard takes with a video-call Picture in Picture window and an active `.playAndRecord` session under the `audio` background mode, so it is a user-enabled window with a visible, fixed deadline (Settings > Keyboard standby: Off, 5, 15 or 30 minutes; the Home screen shows when it ends), never indefinite and not refreshed by use; it records only during a take the user starts. If review objects, the fallback is **Keep microphone open during standby**, which keeps the recording session itself running for the window instead, or standby Off. Typeless and 微信输入法 show the same observable behaviour: the app stays resident after a keyboard dictation and the microphone indicator is off between takes. Typeless's help page "When does app switching happen" (iOS app 2.2.0) says the keyboard briefly opens the Typeless app when it needs the microphone, and marks it on the Speak button: an outlined microphone icon means a switch is coming, a solid one means none is needed; so Typeless also depends on a resident app. 微信输入法 3.0 added a voice standby duration (语音待机时长) and 3.4.1 a floating-window mode (悬浮窗免跳转, reported 2026-03: after one switch the app stays usable without switching for a long time), which points to a Picture in Picture window keeping its app resident. How either app starts the microphone from the background is not documented; on iOS 27.0.1 this app could not under a silent output (see Standby above).
- Picture in Picture for an app that shows no video is a review risk: guideline 2.5.4 and the Picture in Picture documentation describe it for video playback and video calls, and `ContentSource(activeVideoCallSourceView:)` is meant for an active call. The window here shows only a status, so review may treat it as a background-residency device. Precedents: Typeless ships the same user-facing mechanism as "Skip app switching" (a Picture in Picture window dragged to the screen edge, microphone on only while speaking), 微信输入法's floating-window mode (悬浮窗免跳转) behaves the same way, and the open-source AgenBoard keyboard implements it with video-call Picture in Picture. Mitigations: standby stays user-enabled with a fixed deadline, the window states what it is ("VoiceDraft on standby" / "Recording"), closing it ends standby, and **Keep microphone open during standby** or standby Off remain as fallbacks if review objects.
- The setup guide uses only the public Settings deep link `openSettingsURLString`, and detects enablement only through the keyboard's own presence marker.
- Microphone, and nothing else, is requested by the container app, with a usage string that covers in-app and keyboard dictation, says audio goes only to the provider the user configured, and says that during standby the microphone opens only while the user holds to talk unless they keep it open, and that audio outside a take is discarded.
- The App Privacy answer is "data not collected": the developer operates no service that receives user data.

The keyboard sets the public `UIInputViewController.hasDictationKey` property at initialization and appearance because it supplies its own voice input; this suppresses the redundant system dictation button. Apple documents this under [Indicate dictation support](https://developer.apple.com/documentation/uikit/configuring-a-custom-keyboard-interface?language=swift). The system globe remains available.

The keyboard is voice only. Its layout separates editing from submission: a labeled delete key sits at the upper right beside a small VoiceDraft wordmark, a large blue recording surface combines the microphone and instructions in the middle, and the bottom row contains insert-last-result, space and return. Delete and return never share a row, including in compact layouts; their hit-area edges are 160 pt apart in portrait and 108 pt apart at the 216 pt compact height. Return follows the host's search/send/return label and uses a blue tint. The recording surface is 124 pt high in portrait and 84 pt in compact mode; its text also accepts the same recording gestures. No voice/Pinyin/English selector is added. Recording uses a red surface with a microphone/stop icon and a live amplitude waveform below the instruction; processing shows a progress indicator. Existing tap-to-lock and hold-to-talk gestures, repeated deletion and insertion remain unchanged. Portrait content is 276 pt when the system supplies the globe below the extension, or 320 pt when `needsInputModeSwitchKey` requires our own; compact landscape uses 216 pt. Buttons retain at least 44 pt hit areas and accessibility labels. It has no letter, number or punctuation keys, and users type with the system keyboard or another installed keyboard. Basis: guideline 4.4.1 requires a next-keyboard key, working without Full Access, not launching other apps, and providing keyboard functionality, and it does not require character keys. Dictation-only keyboards such as Wispr Flow, and emoji and GIF keyboards that type no characters, have shipped on the App Store. If review objects, the fallback is a minimal QWERTY page; the deleted typing code is in git history at `fe2ecb0` (`ios/VoiceDraftKeyboard/KeyboardKeysView.swift`).

## Build

```sh
xcodebuild -project ios/VoiceDraft.xcodeproj -scheme VoiceDraft \
  -destination 'platform=iOS Simulator,name=iPhone 17' build CODE_SIGNING_ALLOWED=NO
```

The project links the root package product `VoiceDraftCore`. `swift test --disable-sandbox` at the repository root remains the shared test entry point. iOS-only code is tested by the `VoiceDraftiOSTests` target (status policy, shared result, take state machine, AppModel takes with silent audio and in-memory keys, local store round trips); run it with the same command and `test` instead of `build`, or `VOICEDRAFT_IOS=1 ./scripts/test-all.sh`. Nothing in these tests touches the microphone, the Keychain or the network.

For installing on a physical iPhone (Personal Team signing, one-time App Group registration in the Xcode GUI, hardware UDID destination, 7-day profile expiry, devicectl commands), see the Device build section of `ios/README.md`.
